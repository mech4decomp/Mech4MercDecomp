# Architecture

## The oracle idea

The target binaries were compiled with Microsoft Visual C++ 6.0. To reproduce
them byte-for-byte, each function is transcribed from its original machine code
into a `__declspec(naked)` MSVC6 inline-assembly function. The compiler emits
the transcribed instructions directly; no C++ code generation is involved.

Every `func_<VA>.c` source is therefore both:

- a readable, annotated record of the function's instructions and behavior, and
- an input to a build that must reproduce the reference bytes exactly.

The result is an **oracle**: a source tree that compiles to the canonical
binary. It is not an attempt to recover the original C++ source.

## Source layout

Sources are organized by binary target and PE section, not by subsystem:

```
src/
  mw4mercs/
    text/        func_<VA>.c + in-.text data_<VA>.c
    artifacts/   committed CSV metadata
  blade/
  gundll/
  language/
  missionlang_mercs/
  mw4stats/
  zloglib/
```

Filenames are canonical: `func_<8-hex-va>.c` and `data_<8-hex-va>.c`. Semantics
live in the file header and inline comments, never in the filename. The
per-binary subsystem indexes under `docs/master_index/` provide the semantic
map.

Non-`.text` sections (`.rdata`, `.data`, `.rsrc`, `.txt2`) are byte-exact data
runs. They are generated locally from the user's reference and are not
committed; see `BUILD.md`.

## Building an image

The EXE build has four stages:

1. **Compile `.text` sources** — all `src/mw4mercs/text/*.c` are compiled with
   the pinned MSVC6 flags into `build/obj/`.
2. **Generate data sections** — `exe_data_assemble.py --files` reads the
   reference, emits byte-exact `data_0x*.c` sources for the non-`.text`
   sections, compiles them into `build/obj/data/`, and verifies their bytes.
3. **Extract metadata** — `exe_image_assemble.py --init` writes the PE header,
   inter-function pad bytes, and the residual extern-address table. The extern
   table is learned from the compiled `.text` objects, so this step must run
   after step 1.
4. **Assemble** — `exe_image_assemble.py` places every object at its reference
   RVA, resolves relocation sites, fills pads, composes the sections, and
   writes `build/MW4Mercs.exe`. `--diff` compares the result to the reference.

Module DLLs use the same model with `data_assemble.py` and
`image_assemble.py`. gundll's in-scope VA list is provided at
`reference/in_scope/gundll.txt` for its coverage report.

## Relocation resolution

An unlinked object's relocation slots contain placeholder values. The
assembler resolves each slot from the symbol name:

1. Address-embedded names (`FUN_00401000`, `g_0076B000`, ...).
2. The committed `src/<target>/artifacts/extern_addrs.csv` table for residual
   symbols whose names carry no address.
3. The import map parsed from the assembled `.rdata` for imported functions.

The committed extern table is authoritative. The source-comment fallback is
legacy and must never drive the build; the assembler hard-errors if a symbol
would resolve that way.

## Verification model

There are three levels of checking:

- **Masked per-function diff** — compares one compiled object against the
  reference function, masking 4-byte relocation sites.
- **No-mask per-function check** — places the object at its VA, resolves every
  relocation, and compares every byte.
- **Full-image assembly** — composes the complete binary and compares it to the
  reference with no masking. This is the acceptance gate.

The full-image gate is the strongest: it catches ordering, padding, alignment,
relocation, and section-composition errors that per-function checks cannot.

## What is intentionally out of scope

- The `.txt2` SafeDisc leftover (preserved only as generated bytes for layout).
- DRM/SafeDisc components and the bundled DRM DLLs.
- CRT and middleware code that is not game logic.
- The four editor/config tools shipped with the game (documented under
  `docs/editor_tools/`, not oracle targets).
- `ScriptStrings_MERCS.dll` (resource-only, no code).
